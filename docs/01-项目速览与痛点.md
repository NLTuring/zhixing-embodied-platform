### 1.2 项目简介（四种长度，按场合直接取用）


#### （1）一句话版（约 25 字，用于标题、封底、名片）

让具身智能的任务规划可验证、可比较、可复现。


#### （2）摘要版（约 120 字，用于报名表、路演开场）

知行是一套面向具身智能的任务规划中间件与仿真评测平台。它把大模型生成的"看起来合理"的计划，接到真实机器人能执行的动作上：向上统一异构机器人与仿真器的技能表示，向下用仿真做在环验证，把不可行的计划诊断出失败原因并自动修复，最终给出一套可复现、可比较、可向真机迁移的评测结论。


#### （3）标准版（约 380 字，用于商业计划书摘要页、PPT 第二页）

具身智能正在从论文走向产线，但一个尴尬的现实是：大模型写出的任务计划常常"说得通、做不到"。把"把桌上的杯子收进柜子"拆成十步，语言上毫无破绽，落到具体机器人身上却可能第一步就不可达、第三步就碰撞、第五步抓不稳；更麻烦的是失败之后没人知道是哪一步、为什么失败，只能靠人工反复改提示词。与此同时，每个团队都在为自己的机器人、自己选的仿真器重写一套技能接口与评测脚本：同一个任务换一个本体就要重做一遍，同一个模型换一个基准成功率就换一个数字，"谁强谁弱"无法回答。

知行提出以"技能抽象 + 仿真在环验证"为核心的双层内核：用统一的技能表示与本体能力模型，把语言层的任务分解与不同机器人、不同仿真器的动作空间对齐；再把仿真器当作规划器的一部分，构建"规划—验证—诊断—修复"的闭环，让每一个不可行计划都能被定位原因、自动修复，并输出带置信度的可执行性度量。在此基础上，平台提供跨本体、跨仿真器的可复现评测协议与迁移性指标，把"仿真里的高成功率"第一次与"真机上的表现"建立起可量化的相关性。

产品由中间件运行时、仿真评测平台与评测认证服务三层组成，目标用户是具身智能整机厂商、高校与科研院所、创新中心与第三方检测机构。我们不做机器人本体，也不重写底层运动控制，只做本体之上那一层最缺的"规划与评测底座"。


#### （4）详版（约 720 字，用于申报书立项背景首段）

具身智能被列入国家未来产业培育方向，人形机器人与通用机器人正在成为新一轮产业竞争的焦点。与产业热度形成反差的是工程现实：把一个大模型接上机器人，让它在真实环境里完成一段较长的任务，仍然是一件成功率低、调试成本高、结论不可比较的事。问题不在于大模型"不够聪明"，而在于从语言到动作这一整条链路上，有三处结构性的断层至今没有被系统的方法填上。

第一处断层在"计划"与"物理"之间。语言模型生成的任务序列在语义上自洽，却不携带几何与动力学约束，因此在具体本体上频繁出现不可达、碰撞、抓取失败、前置条件不满足等问题；而且这类系统普遍是开环的——计划一旦生成就直接执行，失败之后既没有失败原因的定位，也没有把失败反馈回去的机制。研发者的日常因此退化为"改提示词、重跑、看运气"。

第二处断层在"本体"与"本体"之间。技能接口、任务表示、仿真环境在不同团队之间完全不统一，同一个任务换一个机器人就要把接口与脚本重写一遍。这意味着整个行业在重复支付同一笔工程成本，而本该被复用的技能与经验无法沉淀。

第三处断层在"仿真"与"真机"之间。现有评测大多以"最终成功率"为单一指标，且任务集、环境与评价协议各不相同：换一个基准，排名就可能翻转；仿真里 90% 的成功率，也缺乏与真机表现之间相关性的量化证据。这使得技术选型、产品准入与标准制定都缺少可依赖的依据。

知行的核心贡献，是把这条链路上的三处断层作为三个可计算的问题来处理：用"统一技能抽象与本体能力模型"消除本体间的表示差异；用"仿真在环的可执行性验证与规划修复"把开环规划变成闭环；用"迁移性可复现评测协议"让仿真结论具备可比较性与向真机迁移的可信度。技术上采用"通用能力用成熟开源组件兜底、创新火力集中于技能抽象与验证闭环"的策略，在工程可靠性与方法先进性之间取得平衡。项目当前处于【待填：完成情况】阶段，已在【待填：仿真器 / 本体】上实现【待填：主要能力】，任务一次规划可执行率达【待填】。

## 第二章  项目背景与痛点

本章对应商业计划书的"痛点与市场机会"章节、PPT 的第 2–3 页。写作要求：每一条痛点后面必须跟一个数字或一个可复现的失败案例，禁止只使用形容词。


### 2.1 背景：三浪叠加

本项目处在三股浪潮的交汇点上，它们共同放大了"计划说得通、机器人做不到"这个问题的严重性，也共同决定了为什么是现在。

- 第一浪·大模型的规划能力刚刚越过可用门槛。语言与视觉大模型第一次让"用自然语言描述任务、由模型拆成步骤"成为可行路径，具身智能从此前的专用任务脚本，转向"通用模型 + 具体本体"的新范式。但范式转换也把一个新的问题推到前台：模型输出的是文本，机器人需要的是动作，这中间的映射没有任何人负责验证。

- 第二浪·仿真器生态开源化、算力成本下探。Isaac Sim / Isaac Lab、MuJoCo 与 MJX、Genesis、Gazebo 等仿真器陆续开源或免费可用，GPU 并行仿真把"跑一次评测"的成本从数天压到数十分钟。这意味着一件以前做不到的事第一次变得可行：把仿真直接放进规划回路，让每一个候选计划都先被物理引擎"试一遍"。

- 第三浪·具身智能的产业需求与标准需求同时爆发。整机厂商要在多种本体上快速验证算法，创新中心与检测机构需要可复现的准入测评手段，高校实验室需要能横向比较的基准。产业刚刚起步，评测口径尚未固化，正是中立第三方平台建立影响力的窗口期。

三浪叠加的结果是：具身任务规划已经从"能不能做"进入"做得靠不靠得住、比不比得出来"的阶段，而对应的验证与评测工具供给几乎为零。


### 2.2 痛点一：规划与执行断层——"计划说得通，机器人做不到"

这是本项目最根本的立足点。当前主流的具身任务规划方案是"大模型直出计划"：把任务描述与可用技能列表交给语言模型，模型返回一串步骤，系统按顺序执行。这个方案在演示视频里表现亮眼，在真实调试中暴露三个问题。

| 问题 | 具体表现 | 后果 |
|---|---|---|
| 语义合理但物理不可行 | 模型不了解本体的可达空间、负载能力与几何尺寸，生成的步骤可能包含不可达位置、穿模抓取、超出行程的动作 | 计划在第一步或前几步就中断，成功率高度依赖运气 |
| 开环执行，失败无诊断 | 计划生成后直接执行，失败时只能得到一个"整体失败"的结果，无法定位到具体步骤与具体原因 | 调试退化为改提示词重跑，同一问题反复出现 |
| 无置信度，无法预筛 | 系统不输出"这个计划有多大概率可执行"，也就无法在多个候选计划中择优，或对高风险步骤提前人工介入 | 算力与时间被消耗在注定失败的计划上 |

这个断层带来一个可以被现场证实的失败案例：把同一个语言模型、同一套技能描述，按公开方法接到两个不同的机械臂本体上，统计"语义上成立但物理上不可行"的计划占比。这一步复现成本低、结论直观，是答辩第 3 页最有冲击力的素材（证据形态见 2.5）。

需要强调的是：这不是"模型不够强"的问题。即使换成更强的模型，只要物理可行性不由某一步显式校验，问题结构就不会改变。真正缺的是一个把可行性校验放进规划回路的机制。


### 2.3 痛点二：本体与仿真器碎片化——同一件事被重复做 N 遍

具身智能的工程现实是：技能接口、任务表示、仿真环境在团队之间完全不统一。一家公司换一款机器人，一个实验室换一个仿真器，甚至同一个团队换一个任务批次，都要重写一套接口与脚本。

| 断层位置 | 现状 | 造成的后果 |
|---|---|---|
| 技能表示不统一 | 抓取、放置、开门、推拉等技能在每套系统里各写一份代码，接口、参数、单位、坐标系约定各不相同 | 技能无法跨本体、跨团队复用，每个新本体都是一次从零开始 |
| 本体描述不统一 | URDF / SDF / 厂商私有格式并存，尺寸、关节限位、负载、传感器配置分散在各自的模型文件里 | 规划器无法在生成计划前就知道"这个本体能不能做这件事" |
| 仿真器接口不统一 | Isaac Lab、MuJoCo、Genesis、Gazebo 的 API、场景格式、时间步与控制接口互不兼容 | 同一批任务在不同仿真器上要重新适配一遍，评测结果也无法跨仿真器比较 |
| 评测脚本不统一 | 每个基准自带一套任务集、指标定义与打分脚本 | 换一个基准排名就可能翻转，横向比较失去意义 |

这个痛点的量化方式很直接：让一名成员把同一个技能（例如"抓取并放置"）从一个本体迁移到第二个本体，记录所需的工时与代码改动量（人日 / 行数）。这个自测数字既是痛点二最硬的证据，也是本项目"技能复用率"指标的基线（见 5.2 与附录 E）。


### 2.4 痛点三：评测缺位——"仿真里的成功率说明不了什么"

这是本项目最具公共价值的一层痛点，因为它解释了为什么整个领域的进展难以被度量。

| 环节 | 现状 | 造成的后果 |
|---|---|---|
| 指标单一 | 多数基准以"最终任务成功率"为唯一或主导指标，不区分"哪一步失败""失败原因是什么""部分完成度多少" | 模型 A 比模型 B 高 3 个百分点，无法说明差在哪里、是否值得改 |
| 协议各异 | 任务集、场景、随机化范围、评分标准、超时阈值各不相同，且多以论文附带脚本的形式存在 | 结果不可复现、不可比较；复现一篇工作的成本高于重做一次实验 |
| 缺迁移性证据 | 仿真与真机之间的相关性缺乏量化研究，也没有把迁移性作为评测指标的通行做法 | "仿真里 90%"不能推出任何真机结论，技术选型缺少依据 |
| 无准入口径 | 缺少面向工程与准入的评测服务：企业无法委托第三方对算法或本体做标准化测评 | 产业缺少中立、可复核的质量依据，标准制定缺少数据支撑 |

因此本项目要回答的，不是"能不能让机器人完成任务"（学术界已有大量工作），而是**"如何让任务规划的结果可验证、可比较、可迁移"**。这就是科学问题的来源。

## 第三章  产品与解决方案

本章对应商业计划书的"产品与服务"章节、PPT 的第 4 页与第 7 页。写作要求：讲清楚"输入什么、输出什么、用户操作几步、比现状好在哪"。


### 3.1 产品定位

一句话定位：把大模型"说得通"的计划，变成可验证、可修复、可比较的机器人执行序列。

定位的三个关键限定，请在商业计划书中反复强调，避免评委误解为"又一个仿真软件"或"又一个机器人中间件"：

- 不做机器人本体，也不重写底层运动控制与抓取算法。我们做的是本体之上那一层：把任务规划与物理可行性、以及跨本体的差异隔离开。

- 不做又一个仿真器，而是把已有的仿真器当成规划回路里的验证器。我们的价值在于"用得上、用得省、用得可比"，不在于重造物理引擎。

- 不止步于跑分，还给出可诊断、可修复、可迁移的工程闭环。每条结论都回答"哪一步失败、为什么失败、怎么修、真机上有多大把握"。


### 3.2 三层产品形态

| 层级 | 形态 | 面向用户 | 价值主张 |
|---|---|---|---|
| L1 内核 | 跨本体技能抽象与任务规划引擎（Python / C++ 核心，可作为 SDK 与 API 输出） | 具身智能整机厂商、仿真器与机器人软件厂商、高校实验室 | 被集成，形成技能库与事实标准 |
| L2 平台 | 中间件运行时（多仿真器 + 多本体适配）+ 评测云平台（批量任务评测、可视化、报告导出） | 整机厂商算法团队、高校与科研院所、集成商 | 直接付费的主力产品 |
| L3 服务 | 标准化评测报告与认证服务 + 私有化部署 + 联合基准与标准建设 | 具身智能创新中心、第三方检测机构、地方政府、大型企业 | 高客单价、强公信力壁垒 |


### 3.3 核心功能清单

| 功能模块 | 具体能力 | 解决什么问题 |
|---|---|---|
| 多仿真器适配 | 统一接入 Isaac Lab、MuJoCo / MJX、Genesis、Gazebo；统一的场景加载、时间步控制、状态读取与重置接口 | 换一个仿真器就要重写一遍适配代码 |
| 多本体适配与能力模型 | 解析 URDF / SDF / 厂商模型，自动提取可达空间、关节限位、负载、传感器配置，生成可被规划器查询的本体能力模型 | 规划器不了解本体能力，生成物理上做不到的计划 |
| 统一技能抽象层 | 把抓取、放置、推拉、开门、导航等技能表示为统一的"前置条件—效果—参数空间—本体映射"四元结构，并提供技能库的版本管理与复用 | 技能无法跨本体、跨团队复用 |
| 约束感知的任务分解 | 在结构化输出约束与技能前置条件下让大模型完成任务分解，输出带不确定度的任务图与技能序列，并前置过滤明显不可行的候选 | 模型输出不可解析、幻觉步骤多 |
| 仿真在环验证 | 把候选计划送入仿真执行，输出成功率、几何可行性、时间与能耗、安全裕度四类可执行性度量 | 计划可行与否没有客观判定 |
| 失败模式诊断 | 按不可达 / 碰撞 / 抓取失败 / 前置条件不满足 / 超时 / 语义歧义等类别自动归因，并定位到具体步骤 | 失败之后不知道为什么失败 |
| 规划自动修复 | 把失败诊断转化为约束（反例）回灌规划器，触发局部重规划或技能参数调整，形成闭环 | 只能人工改提示词重跑 |
| 批量可复现评测 | 固定随机种子与配置，批量执行任务集，输出可复现的指标与统计显著性；支持跨本体、跨仿真器、跨模型对比 | 结果不可复现、不可横向比较 |
| 迁移性评估 | 在域随机化条件下评测，输出仿真—真机相关性的量化指标与真机小样本验证流程 | 仿真结论无法支撑真机决策 |
| 可视化与调试 | 计划树、执行轨迹、失败点回放、技能调用序列与指标看板；支持一键导出评测报告 | 调试过程不可追溯、报告不可交付 |
| 报告与存证输出 | 面向厂商的算法评测报告；面向检测机构的标准化测评报告；面向科研的可复现实验包（配置 + 种子 + 结果） | 缺少可交付、可复核的第三方依据 |


### 3.4 标准使用流程（PPT 建议用流程图呈现）

用户实际只需三步，适配与验证全部由平台完成：

- 第一步·接入。导入本体的模型文件（URDF / SDF 或厂商格式），选择仿真器，平台自动生成本体能力模型并完成技能库的初始映射；真机侧通过 ROS 2 接口接入，无需改动底层控制。

- 第二步·规划与验证。用自然语言给出任务，平台生成候选计划，在仿真中批量执行并输出可执行性度量；失败的计划被自动诊断原因并修复，直到通过或在预算内放弃，全过程可回放。

- 第三步·评测与交付。把模型、本体、任务集组合成一次评测，平台输出可复现的指标报告与对比结果；需要对外证明时，可申请标准化的第三方测评报告。

关键对比：现状是"改提示词 → 真机试 → 失败 → 再改"，一轮数小时到数天，且结论不可复现、不可比较；本产品是"自然语言任务 → 仿真批量验证 → 自动诊断修复 → 可复现报告"，一轮数十分钟，结论可复核、可横向比较。
