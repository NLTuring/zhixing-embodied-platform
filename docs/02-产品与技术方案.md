# 产品与技术方案


## 第四章  技术方案

本章对应商业计划书的"技术与研发"章节、PPT 的第 5–7 页。写作要求：让技术评委相信方法成立，让非技术评委相信学生团队做得出来。


### 4.1 统一理论内核：四级映射、四个缺口、两个构造

这是项目最重要的理论贡献，建议在商业计划书中用一整页专门说明。

观察：具身任务规划本质上是一条**从语言到动作、再回到可信结论**的映射链。从自然语言任务出发，到最终可迁移的评测结论，中间隔着四级映射，而每一级都存在缺口：

```
自然语言任务 → 任务图/子目标 → 技能序列 → 本体动作与物理执行 → 可迁移的结论
                                        （仿真中）
     └缺口一┘      └缺口二┘     └───缺口三───┘        └缺口四┘
   语言→结构化     任务→技能        技能→物理          仿真→真机
   （创新点一）    （创新点二）     （创新点三）        （创新点四）
```

| 缺口 | 缺口的本质 | 现有技术只填补到哪一步 |
|---|---|---|
| 缺口一<br>语言→结构化 | 自然语言的任务意图落不到可约束、可校验的任务结构上；模型自由生成文本，输出不可解析、步骤幻觉频发 | 提示工程与结构化输出能提高解析率，但不把本体能力作为约束注入，也不输出不确定度 |
| 缺口二<br>任务→技能 | 技能在不同本体与不同团队之间没有统一表示，一个技能无法被另一个本体直接复用 | 传统任务—运动规划（TAMP）在单一本体内部做得很扎实，但跨本体的表示与复用无人负责 |
| 缺口三<br>技能→物理 | 技能序列只保证逻辑前后一致，不保证几何与动力学可行；失败之后没有原因定位与反馈机制 | 单一仿真基准能给出"最终成功率"，但不做失败归因，更不把失败回灌到规划 |
| 缺口四<br>仿真→真机 | 仿真结论与真机表现之间的相关性缺少量化证据，评测协议彼此不通，排名不可比 | 各基准自成一套脚本与指标，没有统一协议，也没有把迁移性当作指标 |

没有任何现有方法把这条链整体打通，并让每一级的失败可定位、可修复、可传递。本项目给出两个核心构造，把这条链变成一个可计算、可改进的整体。四个缺口与四条创新点一一对应（见第五章）。


#### 构造一：统一技能抽象与本体能力模型

核心判断：只要技能被表示为"前置条件—效果—参数空间—本体映射"的显式结构，规划就从一个语言问题变成一个可满足性问题；而只要本体的能力被显式建模，"这个本体能不能做这件事"就可以在生成计划之前被回答。

```
技能 s = 〈 Pre(s), Eff(s), Θ(s), Φ_b(·), c(s) 〉
  Pre(s) 前置条件；Eff(s) 效果（状态转移）；Θ(s) 参数空间；
  Φ_b(·) 技能在本体 b 上的映射（含参数标定）；c(s) 成本与风险估计

本体能力模型 C_b = 〈 R_b 可达空间, L_b 负载, n_b 自由度,
                     传感与执行配置, Skills(b) 技能集合 〉

规划： Π* = argmax_Π  Σ_i  u( s_i ; C_b )
  s.t.  Pre(s_1) = I ,  Eff(s_n) ⊇ G          （起点与目标）
        Pre(s_{i+1}) ⊇ Eff(s_i)                （因果链一致）
        s_i ∈ Skills(b)                        （本体可执行）
        θ_i ∈ Θ(s_i) ∩ 可行域(C_b)              （参数可行）
```

这个构造的价值是"一次建模、多体复用"：技能库与本体能力模型都被显式化之后，新增一个本体只需提供能力模型与少量映射标定，而不必重写技能代码；技能库也可以像软件包一样被团队之间共享与版本管理，形成生态。同一个技能在本体 A 上写的一次，成为本体 B 上可直接调用的资产。


#### 构造二：仿真在环的可执行性验证与规划修复闭环

核心判断：把仿真器当作规划器的一部分，而不是规划后的验收工具。每一次规划提议都先在物理引擎里"试一遍"，用可执行性度量判定，把失败诊断成约束再回灌规划器。

```
可执行性度量（四元组）：
  E(Π) = 〈 p_succ 成功率, κ_geo 几何/动力学可行性,
           τ_cost 时间与能耗, ρ_safe 安全裕度 〉

失败诊断：  f = D( trace )
  f ∈ { 不可达, 碰撞, 抓取失败, 前置条件不满足, 超时, 语义歧义 }

修复重规划： Π′ = Plan( T , Skills , C_b , ¬f )
  即把失败原因作为反例约束回灌规划器，触发局部重规划或技能参数调整

闭环： Plan → Simulate → Diagnose → Repair → Plan → … → 通过 / 预算耗尽
```

| 闭环的产出 | 具体形态 | 用途 |
|---|---|---|
| 判定 | 每个候选计划的可行/不可行判定，以及经过校准的置信度与区间 | 在候选计划之间择优，避免把算力花在注定失败的计划上 |
| 归因 | 失败原因的类别与发生步骤，附执行轨迹回放 | 把"整体失败"变成"第 3 步碰撞"，调试从猜变成定位 |
| 资产 | 累积的失败模式库：可按技能与本体统计的高频失败原因，用于自动修正技能的前置条件与参数默认值 | 让每一次失败都变成可复用的经验——这是单纯增大模型规模拿不到的东西 |

这个构造的价值同样是"一个闭环、三种产出"：它同时解决了可行性判定、失败归因与经验沉淀三个问题，而不是三套独立机制。这也是本项目与"再加一层提示工程"最本质的区别——我们的规划器有一个会说实话的物理世界在监督它。


### 4.2 技术架构：五层处理管线

数据从 L0 接入层进入，依次经过 L1 抽象、L2 规划、L3 验证三个处理层，由 L4 评测层完成规模化度量与交付。

| 层级 | 名称 | 核心职责 | 关键输出 |
|---|---|---|---|
| L0 | 接入层 | 仿真器适配（Isaac Lab / MuJoCo / Genesis / Gazebo）；本体适配（解析 URDF / SDF / 厂商模型）；真机适配（ROS 2 接口） | 统一的场景、本体与执行接口 |
| L1 | 抽象层 | 统一技能表示与技能库管理；本体能力模型构建与校验；跨本体技能映射与参数标定 | 技能库 + 本体能力模型 |
| L2 | 规划层 | 约束感知的任务分解与任务图生成；候选计划采样；前置条件与能力约束的注入与过滤 | 候选计划集合（带不确定度） |
| L3 | 验证层 | 仿真批量执行；可执行性四元组计算；失败模式诊断；反例约束回灌与修复重规划 | 通过的计划 + 失败归因 + 经验条目 |
| L4 | 评测层 | 多任务 / 多本体 / 多仿真器批量评测；六项指标计算与统计显著性检验；报告生成与榜单发布 | 可复现的评测报告与基准结果 |

架构的核心设计意图：L2 与 L3 之间不是单向流水线，而是共享同一个**计划对象与执行轨迹对象**——每个候选计划携带"来自哪些技能、在哪些本体上标定过、置信度多少"，执行轨迹携带"哪一步失败、失败原因是什么"，这两个对象在向上聚合时被完整传递，最终出现在评测报告与失败模式库里。这正是"每条结论都可追溯、每次失败都可复用"的工程实现方式。


### 4.3 关键技术模块

| 模块 | 技术路线 | 说明 |
|---|---|---|
| 约束感知的任务分解 | 结构化输出（JSON Schema / 语法约束解码）+ 技能前置条件作为可满足性约束；输出任务图与技能序列，并附步骤级置信度 | ★ 创新点一的载体；把"提高解析率"升级为"把能力约束注入生成过程" |
| 统一技能抽象 | 技能的六元组表示 + 技能库（版本管理、依赖、跨本体映射） | ★ 创新点二的载体；技能库规模与复用率是可量化指标 |
| 本体能力模型 | 从 URDF / SDF 自动提取关节限位、连杆几何、负载与传感配置，生成可被规划器查询的能力描述；结合标定实验修正 | 决定规划器能否在生成计划前做可行性预筛 |
| 几何与动力学可行性校验 | 正逆运动学（Pinocchio）、碰撞检测（FCL / 凸包近似）、可达空间与抓取稳定性分析；可选接入 cuRobo 做 GPU 加速 | κ_geo 的计算来源；未通过即触发诊断与修复 |
| 失败模式诊断 | 规则 + 学习的混合归因：先按物理判据分类（不可达 / 碰撞 / 抓取失败 / 前置不满足 / 超时），再用轨迹特征细分原因 | ★ 创新点三的关键；诊断准确率以人工标注为真值 |
| 规划修复与反例回灌 | 把失败原因转写为约束并注入下一轮规划；支持局部重规划、技能参数调整、技能替换三级修复策略 | 形成闭环；修复策略的优先级由失败模式库的统计结果驱动 |
| 并行仿真与批量评测 | GPU 并行仿真（Isaac Lab / MJX）+ 任务队列调度；固定随机种子与配置快照，保证可复现 | 把"跑一次评测"从数天压到数十分钟，是闭环可行的前提 |
| 域随机化与迁移性评估 | 对光照、纹理、摩擦、质量、时延、传感噪声做参数化随机化；在真机小样本上做相关性分析（Spearman 秩相关） | ★ 创新点四的关键；仿真结论可信度的量化依据 |
| 多本体映射与标定 | 同一技能在不同本体上的参数标定流程与工具链；标定结果版本化，随本体模型一同管理 | 技能复用率与新增本体接入工时的直接决定因素 |
| 可解释与可追溯 | 每个结论标注证据来源（计划 / 轨迹 / 技能 / 本体 / 种子）、样本量与置信区间；报告可一键导出 | 直接回应"我凭什么信这个结果" |
| 数据与许可合规 | 仿真器与模型许可合规清单（Isaac Sim / MuJoCo / Genesis 等各自的许可条款）；用户任务集与真机数据授权、用途限定、可删除；提供完全离线的本地部署模式 | 答辩必问项，必须在 BP 中写明 |


### 4.4 技术栈与可行性

技术策略：通用能力使用成熟开源组件兜底，创新火力集中于"技能抽象"与"验证修复闭环"两个环节。这一策略同时保证工程可靠性、开发速度与创新集中度，也是 6–8 人团队能够做成的前提。

| 模块 | 选型 | 选用理由 |
|---|---|---|
| 仿真器 | Isaac Sim / Isaac Lab（GPU 并行、生态完整）、MuJoCo 与 MJX（轻量、许可友好）、Genesis、Gazebo（ROS 生态） | 多仿真器是"可复现评测"的立身之本；不绑定单一厂商 |
| 机器人中间件 | ROS 2（Humble / Jazzy）+ DDS 通信 | 真机接入的事实标准，避免自造通信层 |
| 运动学与规划 | Pinocchio（运动学/动力学）、MoveIt 2 与 OMPL（运动规划）、Drake（可选，用于形式化校验）、cuRobo（GPU 加速） | 不必重造底层算法轮子，把力气花在技能层与验证闭环 |
| 大模型与视觉 | 开源 VLM / LLM 本地部署（如 Qwen-VL、InternVL 系列）+ 可选云端 API；结构化输出与工具调用 | 本地部署保证数据合规与离线可用；结构化输出是约束感知分解的基础 |
| 学习与训练 | PyTorch；模仿学习与强化学习用于长尾技能恢复与抓取策略 | 只在规则化方法覆盖不到的长尾环节引入学习，控制不确<br>定性 |
| 平台与后端 | Python / FastAPI + PostgreSQL + TimescaleDB（评测时序）+ Redis + 对象存储；任务队列与容器化调度（Docker / K8s） | 批量评测是典型的高并发长任务负载，需要可靠的任务编排 |
| 前端与可视化 | Web 看板（Vue / React）+ 三维回放（three.js / Rerun / Foxglove） | 失败回放与计划树可视化是调试体验的核心 |
| 统计与评测 | Python（scipy / statsmodels）+ R（可选）；置信区间、显著性检验、相关性分析 | 评测结论必须带统计口径，否则不可比较 |
| 硬件（真机验证） | 桌面级 6 自由度协作机械臂 + 移动底盘；可选向合作厂商借测人形或四足本体 | 真机验证只需小样本，目的是标定仿真—真机相关性，而非大规模部署 |

团队技能门槛：核心研发需要"任务规划与约束求解 + 机器人运动学与仿真 + 大模型应用 + 平台工程"的组合。本项目通过分层策略正面回应这一门槛：仿真器与运动规划使用官方接口与成熟库，大模型使用开源权重与结构化输出，创新火力集中在技能抽象与验证闭环——这两个环节恰好不需要庞大的算力与硬件投入，而是需要清晰的抽象能力与工程纪律。


### 4.5 技术指标的承诺边界

以下边界必须主动声明。主动说明比被评委问出来更可信。

- 不承诺通用具身智能。本平台定位为任务规划与评测层的中间件，不替代底层运动控制、抓取策略与感知算法；下层能力的强弱会直接影响上层规划的可执行率。

- 不承诺零样本迁移到任意本体。技能抽象需要按本体做适配与参数标定，标定工作量因本体差异而异；我们能承诺的是"新增本体的接入工时显著下降"，而不是"不需要接入"。

- 不承诺仿真等于真机。我们输出的是"仿真—真机相关性的量化指标与小样本验证证据"，并明确标注仿真结论的适用范围。任何宣称仿真可以完全替代真机验证的说法都不可信。

- 不承诺大模型规划最优。我们提供的是可验证、可修复、可比较的规划流程；在给定预算内可能找不到可行计划，此时系统如实报告"未找到可行计划"及其尝试过的失败模式，而不是给出一个未经校验的答案。

- 不承诺覆盖所有任务类型。首发版本聚焦桌面级操作与室内移动操作的长程任务（抓取、放置、开关、推拉、导航），高动态与强接触类任务明确列为后续版本。
